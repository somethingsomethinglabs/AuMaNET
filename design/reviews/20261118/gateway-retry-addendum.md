# Gateway startup retry finding

Physical investigation used the intended Nothing3a → node B and Z Flip → node A pairing, with the existing identities, keys and membership retained. The hardware operator observed successive gateway generations 48, 49 and 50 with new session IDs, each returning to one emitted packet, zero authenticated boot proofs and no surfaced error while trusted connection remained `connecting-node`. These observations establish repeated startup replacement; they do not establish why node proof failed.

`TrustedConnectionController.ownerGatewayReady` previously started a new gateway job whenever the issuer had no current job. After the gateway's ten-second owner-proof timeout retired its job, ordinary trusted-connection polling therefore created another startup. This hid the prior failure and repeated the original-run bootstrap exception without the explicit node recheck required by `GatewayBootstrapGate`.

The controller now retains the exact previously observed gateway job. If that job disappears or another job replaces it, polling enters the existing `attention` state with `CONNECTION_REQUIRES_ATTENTION`, interrupts owned voice/location readiness, and requires explicit reconnect. It neither adopts a replacement nor emits a new bootstrap. A new explicitly authorized trusted connection can still start normally. An intentional owned gateway retirement for a verified group/network scope switch clears the reference only after a successful exact-session stop, preserving that bounded replacement path. No node-proof checks were relaxed.

Validation: `native-trusted-connection.mjs` passed with 69 tests and 325 assertions, compiling the actual production controller against declared fake Android/group/service/transport boundaries. Regression cases cover a missing owner-proof startup followed by five ten-second polls without replacement, explicit stop/connect recovery without changing the remembered policy revision, externally replaced gateway isolation, and an owned switch to a different network. Result: local `output/host/trusted-gateway-retry/result.json`. This is host evidence; it does not certify physical recovery after installing the change.

Earlier hypotheses of deadlock or a silently terminated periodic task were not confirmed. Operator thread inspection found idle gateway workers; the sampled scheduled future was pending with no failure outcome. A framework exception observed during debugging was handled internally and is not evidence of terminal signing failure. The underlying missing authenticated local-node proof remains unresolved. This change makes the failure visible and stops unauthorized automatic bootstrap replacement; it does not claim to fix proof acquisition. No firmware was changed.
