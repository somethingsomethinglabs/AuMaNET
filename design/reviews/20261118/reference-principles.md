# Reference principles and AuMaNET coverage — 18 November 2026

## Scope and evidence

The nine references below are interpretations of **earlier screenshots**, captured in the `ux-audit` folder on 16 November and summarized in the parent review. They are not a current audit of those live products, evidence that a whole product is usable, or a ranking of globally “best” interfaces. A screenshot can show hierarchy and grouping; it cannot establish completion rates, screen-reader behavior, error recovery or user understanding. The proposed transfers are design hypotheses with concrete checks.

Screenshot folder: `C:/Users/rowan/.codex/visualizations/2026/11/16/01a1e4bb-783f-7500-918a-492b4294c4a8/ux-audit/`.

The assessment uses [Jakob Nielsen's usability heuristics](https://www.nngroup.com/articles/ten-usability-heuristics/) and NN/G's explanations of [proximity](https://www.nngroup.com/articles/gestalt-proximity/), [similarity](https://www.nngroup.com/articles/gestalt-similarity/) and [common region](https://www.nngroup.com/articles/common-region/). These explain why a pattern may work; the judgments and AuMaNET proposals below are our assessment, not findings from a comparative user study.

## The questions behind the choices

**Why choose Duolingo for a clear first decision?** Its observed entry screen asks people to recognize their own situation: starting for the first time or returning. That is a smaller decision than learning the product's internal structure. It is the strongest of these captured references for this particular distinction because both routes are explicit at the same moment. For AuMaNET, the corresponding question is whether a person needs first setup or wants their saved connection back. The physical pass confirms explicit reconnect can preserve the existing group and history; it does not establish that a new user understands setup without assistance.

**Why choose Airbnb for a multi-part task?** Where, When and Who are independently editable but combine into one search. A shared boundary expresses that relationship; internal divisions keep each input identifiable. AuMaNET's comparable tasks include choosing a radio channel and width, or a sharing allowance and duration. Put each task's inputs, consequences and action together, while retaining readable labels on narrow screens.

**Why choose Apple for hierarchy?** Its captured product section makes the subject and next actions easy to locate. The transferable property is a small set of meaningful priorities. On AuMaNET's connection screen, that means actual state, a clear next action and nearby recovery guidance. A large attractive card cannot make an unverified connection ready.

**Why choose Google Maps for contextual controls?** Map controls act on the visible geographic object, and status gives the action meaning. AuMaNET needs to show whether a position is current, whether Follow is active and whether saved maps cover the visible area. This pass implements visible location/follow state and truthful partial-coverage wording, and tests recenter/pan behavior on both phones.

**Why choose Stripe for specialist navigation?** The observed navigation lets different audiences recognize a relevant destination. AuMaNET also serves ordinary communication tasks and specialist link diagnostics. Plain tool descriptions and task groups help people find a test without first understanding the implementation. This pass groups Tools and checks its destinations and return paths.

**Why choose Canva for starting from intent?** Recognizable starting tasks give a broad product a usable entry point. In AuMaNET Settings, descriptions and unordered multiword search let a person look for an outcome such as dark mode or distance units. Clear search recovery prevents a narrow query from trapping the person in an apparently empty settings list.

**Why choose Spotify for distinguishing related entities?** Repeated shape and grouping communicate content types before each item is read. AuMaNET's people and nodes similarly need consistent text, roles and status. The implemented empty-roster recovery and tested member details preserve the entity context; no claim is made that shape alone is accessible or sufficient.

**Why choose Uber for an action with a concrete result?** The captured pickup/dropoff form makes the requested inputs and the next result directly related. AuMaNET's connection test should similarly identify its peer, consent, progress and measured result. Physical tests exercised a completed measurement, explicit Stop and transfer of historical rates into the planner; those rates remain measurements of that attempt.

**Why choose Nintendo for stable navigation?** The captured navigation supplies recognizable routes despite changing page content. AuMaNET's five main destinations should stay predictable while connection, voice and location state change. The installed walkthrough checks those routes and nested settings. This is a navigation lesson, not evidence that Nintendo is the best reference for every interaction.

## Consolidated feature coverage checklist

This checklist is derived from `dev/app/src/lib/ConnectedApp.svelte` and its component tree. Each row is a **source-based test target**, not a physical-phone pass. Existing automated suites are pointers; their existence is not evidence they ran. Parent review adds measured phone results, exact build identity and any unavailable controls. Fixture-only components under `__tests__` are excluded from normal product inventory.

| Feature / component root | Controls and states to cover | Evidence still needed beyond source review |
| --- | --- | --- |
| App shell — `ConnectedApp`, `PanelHeading`, `HelpButton` | Five primary destinations; Settings open/close; nested Back/Escape/Android Back; help dialog close/focus; selected destination; persistent joined-voice strip; foreground/background | Phone Back behavior, keyboard and system-bar interaction; do not infer native lifecycle from browser navigation. |
| Network overview — `NetworkOverview`, `LinkQualityStatus`, `RadioSignalDetails` | Nodes/members/links; selected item; stale/unknown radio readings; tools entry; details | Compare displayed identity and freshness to actual phone/node observations. |
| Connection — `TrustedConnectionPanel`, `NodeWifiPanel`, `OfflineEnrollment` | New setup, saved Resume, connecting, ready, interrupted, disconnect, forget, enrollment errors/cancel/retry | Intended saved Wi-Fi, actual identity preservation and reconnection; firmware DHCP acceptance remains a separate mandatory gate if firmware changes. |
| Device/node details — `NodeList`, `DeviceDetails` | Own/other node selection, member details, status/role, position accuracy/age, firmware-update navigation, close | Confirm selected identity, roles and observed versions; unavailable fields must remain explicit. |
| Group — `GroupRoster`, `GroupPanel` | Profile name, create/join, invitation handling, member selection, roles, membership actions, leave/cancel, empty/error | Two-device membership and role permissions; no loss of identity/history during recovery. |
| Messages — `NativeGroupMessages`, `NativeGroupMessageComposer`, `messages/ImageViewer` | Text draft/send, invalid/blank content, disconnected state, attachment select/preview/cancel/send, retry, image open/close/save, history management, delivery state | Actual peer receipt, interrupted/retry behavior, Android image picker/save, keyboard occlusion and draft preservation. |
| Voice — `NativeVoicePanel`, `NativePtt`, `NativeVoiceStrip`, `NativeVoiceSettings` | Join/leave, mute/deafen, PTT hold/release/cancel, input/output choices, sensitivity draft/apply/discard/reload; pending/unavailable/error | Two-way listening and physical release/lifecycle behavior; UI readiness is not audio acceptance. |
| Maps — `MapPanel`, `maps/GeographicMap`, `MapConnectionsLegend` | Center on own/member/node position, labels, members/connections overlays, selection/details, freshness/accuracy, map style, unavailable position | Actual permission/location, stale fixes and offline rendering; marker/overlay visibility on narrow phones. |
| Map storage — `maps/OfflineAreaPicker`, `MapCentrePicker`, `VectorDownloads`, `GeoscienceDownload`, `GeoTiffImport` | Area/center selection, zoom/size constraints, download progress/cancel/retry/remove, imported files, local coverage, show map | Real download interruptions/storage availability, Android file import and cached map after loss of internet. |
| Settings overview — `LiveSettingsOverview` | Profile edit shortcut, ten descriptive destinations, text search, multiword queries, no results, clear/focus, Developer options | Browser fixture passed; phone focus, text scale and scroll remain measured separately. |
| Appearance — `AppearanceSettings` | Light/Dark, Metric/Imperial, loading/busy, failed persistence, reload/reset | Browser fixture passed; actual Android persistence/restart and OS text scale remain separate. |
| Location/privacy — `NativeLocationPanel` | Own start/stop/cancel, clear fix, permission/settings links, sharing On/Off, pending/denial/failure, lost group/status | Browser failure fixture passed; Android prompts, actual sharing/stop and background notification require physical evidence. |
| Notifications — `NotificationSettings` | Group alerts, permission, blocked/revoked state, runtime suppression versus saved Off, reset/reload, Android settings | Browser fixture passed; actual Android alert/privacy/channel/background behavior remains separate. |
| Internet — `InternetSettings` | Data cap/duration, donation start/stop, donor select/use/stop, usage/time, refresh, unavailable/group change, help link | Real mobile-data/VPN consent, transfer, limits, donor loss and stop behavior. |
| Tools — `ToolsPanel` | Every tool destination and return route; plain task descriptions | Route checks plus each tool’s meaningful failure and cancellation behavior. |
| Connection test — `LinkBenchmarkPanel`, `BenchmarkComparison` | Arm, peer, start/stop, progress, partial/failure, history disclosures, export JSON/CSV, copy rates to planner | Two intended phones, explicit consent, real result identity/units/history and Android export. |
| Bandwidth — `BandwidthEstimator` | Common/detailed numerical assumptions, workload choices, estimates, historical rates, scenario export, test navigation | Invalid/boundary assumptions and export checked by automated suites; estimated results are never radio coverage proof. |
| Radio — `NativeRadioSettingsPanel`, `RadioSettingsPanel`, `ChannelOptimisationPanel` | Actual/proposed values, width/channel, owner gating, Apply/trial/cancel/rollback, refresh, comparative tests/history | Physical changes only when authorized; actual recovery and observed settings on both nodes, not UI-only success. |
| Updates — `NodeUpdatesPanel` | Node/channel/ref/release selection, check status/releases, download/verify, install gating, progress/cancel, exact identity | Do not install merely for UI review. Firmware changes require exact installed identity plus physical DHCP acceptance. |
| Diagnostics — `DiagnosticsSettings` | Collect/refresh/cancel/clear, component details, redacted JSON, copy/save, failures | Actual Android clipboard/download fallback and redaction; no secrets/private bench data in shared artifacts. |
| Developer options — `NativeVoiceDeveloper`, `GatewayDeveloper` | Explicit entry only, specialist diagnostics/actions, exit/back | Inventory specialist controls separately; no fixture/sample/experimental switch on ordinary screens. Do not execute invasive controls to claim UI coverage. |

Executed Settings-side browser checks are recorded in [settings-review.md](settings-review.md). Parallel network, messaging, voice and map reviews supply their own evidence; this source checklist must not silently promote their pending checks to passes.
